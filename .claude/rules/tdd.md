# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.** "이번만 예외"는 없다. 예외가 필요하다고 느껴지면 아래 "변명 차단표"부터 확인한다.

**우선순위**: 프로젝트의 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시돼 있으면 그것을 우선 적용한다. 이 파일은 프로젝트별 규칙이 없을 때 적용하는 **기본값(fallback)**이다.

## 1. 적용 기준

### TDD를 반드시 적용한다
- **비즈니스 로직** (계산, 상태 전이, 분기 규칙)
- **API** (엔드포인트 핸들러, 요청/응답 처리)
- **유틸리티 함수** (순수 함수, 변환/파싱 로직)
- **버그 수정** (고치기 전에 버그를 재현하는 실패 테스트부터 작성)

### TDD가 불필요하다
- **타입 정의** (interface, type alias)
- **설정 파일** (config, 빌드 스크립트)
- **순수 UI** (마크업·스타일만 있고 로직이 없는 컴포넌트)
- **SQL** (마이그레이션, 스키마 정의)

이 목록에 없는 대상이 애매하면, "조건 분기가 있는가"로 판단한다. 분기가 있으면 적용 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않고 다음 단계로 넘어가지 않는다.
- 실패 이유는 **"기능 미구현"**이어야 한다. 오타·임포트 오류·문법 오류로 실패한 것은 RED가 아니다 — 원인을 고치고 다시 실행해 올바른 이유로 실패하는지 확인한다.

### GREEN
- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 지금 테스트가 요구하지 않는 기능·추상화·파라미터를 미리 만들지 않는다.
- 구현 후 **신규 테스트와 기존 테스트 전체가 통과하는지** 반드시 실행해 확인한다.

### REFACTOR
- 중복 제거, 이름 개선, 헬퍼 추출 등 **구조 개선만** 한다.
- 매 변경 후 테스트가 **green으로 유지되는지** 실행해 확인한다.
- 이 단계에서 **새 동작을 추가하지 않는다.** 새 동작이 떠오르면 다음 사이클의 RED로 미룬다.

### 반복
- REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 사실을 발견하면, **그 코드를 삭제하고 RED부터 다시 시작한다.**
- "나중에 참고하려고" 주석 처리하거나 남겨두는 것도 **금지**한다. 완전히 삭제한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용도 낮다. 단순함은 생략 근거가 아니라 작성 비용이 싸다는 근거다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 테스트 없는 코드는 이미 완료된 것으로 취급되어 우선순위에서 밀린다. |
| "시간이 없다" | 테스트 없이 짠 코드의 디버깅 시간이 테스트 작성 시간보다 길다. 지금 아끼면 나중에 더 쓴다. |
| "삭제하면 낭비" | 순서를 어긴 코드는 검증되지 않은 코드다. 남겨두면 "테스트가 통과해서 맞는 코드"라는 착각을 만든다. |
| "프로토타입이다" | 프로토타입은 버려지거나 살아남아 프로덕션이 된다. 둘 중 어느 쪽이든 지금 규칙을 어길 이유가 되지 않는다. |
