# commit: 변경사항 분석 후 커밋

현재 git 저장소의 변경사항을 분석해 논리적 단위로 나누고, 단위별로 컨벤션에 맞는 한국어 커밋 메시지를 작성해 바로 커밋한다. 이 스킬이 호출됐다는 것 자체가 사용자의 커밋 승인으로 간주하므로, 아래 "주의사항"에 해당하지 않는 한 커밋 전에 별도로 승인을 묻지 않는다.

## 워크플로우

### Step 1: 저장소 지침·컨벤션 확인

- 저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 컨벤션이 명시돼 있으면 이 스킬의 기본 포맷보다 그것을 우선한다.
- `git log --oneline -20`으로 기존 커밋 메시지 스타일(접두사, 언어, 포맷)을 확인한다. 기존 커밋이 있고 다른 컨벤션을 쓰고 있다면 그 스타일을 따른다. 첫 커밋이라 기존 이력이 없으면 아래 기본 포맷을 쓴다.

### Step 2: 변경사항 분석

- `git status`로 전체 변경 파일을 확인한다(대형 저장소에서 `-uall` 플래그는 쓰지 않는다).
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 확인한다.
- 변경된 파일의 diff를 실제로 읽고 무엇이 왜 바뀌었는지 파악한다. 파일명이나 디렉터리만 보고 내용을 추측하지 않는다.

### Step 3: 논리적 단위로 분류

- 서로 목적이 다른 변경(예: 기능 추가 + 포맷팅 + 설정 변경)은 섞지 않고 별도 커밋으로 분리한다.
- 분류 기준: 같은 기능·버그·목적을 위한 변경인지, 나중에 함께 리뷰하거나 되돌리는 것이 자연스러운지로 판단한다.
- 하나의 논리적 변경이 여러 파일에 걸쳐 있으면 하나의 커밋으로 묶는다.
- `.env`, 자격증명 등 민감 정보가 포함된 파일은 커밋 대상에서 제외하고 사용자에게 알린다.

### Step 4: 커밋 메시지 작성

단위별로 다음 형식의 한국어 커밋 메시지를 작성한다(저장소에 기존 컨벤션이 있으면 Step 1에서 확인한 그것을 우선한다):

```
<type>: <한 줄 요약>

<선택: 본문 - 이 변경이 왜 필요한지 2~3문장 이내>
```

- `type`은 변경 성격에 맞춰 고른다: `feat`(신규 기능) · `fix`(버그 수정) · `refactor`(동작 변경 없는 구조 개선) · `chore`(빌드/설정/잡무) · `docs`(문서) · `test`(테스트) · `style`(포맷팅).
- 요약은 명령문으로, "무엇을 바꿨는지"보다 "왜 바꿨는지"에 가깝게 간결히 쓴다. 예: "useMemo 추가"보다 "불필요한 리렌더링 방지".
- 본문은 변경 이유가 자명하지 않을 때만 덧붙인다. 코드를 보면 바로 알 수 있는 내용은 쓰지 않는다.

### Step 5: 바로 커밋

- 승인을 묻지 않고 단위별로 구체적인 파일명을 지정해 `git add`한 뒤(와일드카드나 `-A`로 한 번에 올리지 않는다, 의도치 않은 파일이 섞이는 것을 막기 위함) heredoc으로 커밋 메시지를 전달해 커밋한다.
- 커밋 후 `git status`와 `git log --oneline -n <생성한 커밋 수>`로 결과를 확인하고, 단위별 커밋 메시지와 포함 파일을 요약해 보고한다.
- 사용자가 이후에 메시지나 분류 수정을 요청하면 반영한다(이미 만든 커밋을 고칠 때는 "주의사항"의 `--amend` 규칙을 따른다).

## 주의사항

이 스킬은 커밋 실행 자체는 승인 없이 진행하지만, 아래 상황은 되돌리기 어렵거나 사용자 작업을 침해할 수 있으므로 예외적으로 먼저 알리고 확인받는다:

- **커밋 대상 파일에 이미 의도가 불분명한 미커밋 변경이 섞여 있을 때**(예: 이번 요청과 무관해 보이는 변경, 작업 중으로 보이는 미완성 코드): 어떤 파일인지 알리고 포함 여부를 확인받는다.
- **민감 정보(.env, 자격증명 등)가 포함된 파일**은 자동으로 커밋 대상에서 제외하고, 제외했다는 사실만 알린다.
- 그 외의 통상적인 경우(명확한 기능 추가/버그 수정/설정 변경 등)는 승인 없이 바로 커밋한다.

커밋 실행 방식 자체에 대한 규칙:

- 새 커밋을 생성하는 것이 기본이며, 사용자가 명시적으로 요청하지 않는 한 `--amend`는 쓰지 않는다.
- hook을 건너뛰는 `--no-verify`는 사용자가 명시적으로 요청한 경우에만 쓴다.
- pre-commit hook이 실패하면 원인을 고치고 다시 커밋한다. hook 실패로 커밋이 생성되지 않은 상태에서 `--amend`를 쓰면 이전 커밋을 건드리게 되므로 쓰지 않는다.
- push는 사용자가 별도로 요청하지 않는 한 하지 않는다.
